# Scribe — frontend

The demo's single-page app. **One frontend, any backend**: it speaks
[`examples/openapi.yaml`](../openapi.yaml) and nothing else, so pointing it at the Rust, Java or
TypeScript implementation is one environment variable and no code change.

Stack: Vite + React + TypeScript. No UI framework, no state library, no router package — the point
of this app is the Meteroid surfaces, and a reader should not have to learn three dependencies
before finding them.

---

## Run it

```bash
npm --prefix examples/frontend install
npm --prefix examples/frontend run dev
# http://localhost:5173, talking to http://localhost:8080
```

Start a backend first, or the app boots straight into "No Scribe backend answered at …".

### Point it at a different backend

`VITE_API_BASE_URL` is the only switch. It is read from `examples/.env` (the same file the backends
read — `vite.config.ts` sets `envDir: ".."`), or from the shell:

```bash
VITE_API_BASE_URL=http://localhost:8080 npm --prefix examples/frontend run dev   # Rust
VITE_API_BASE_URL=http://localhost:8081 npm --prefix examples/frontend run dev   # Java
VITE_API_BASE_URL=http://localhost:8082 npm --prefix examples/frontend run dev   # TypeScript
```

Vite inlines the value at build time, so change it and restart the dev server; a production build is
pinned to whatever was set when it was built.

The session token is namespaced by base URL in `localStorage`, so switching backends mid-session
does not carry a workspace across — each backend gets its own. (Share `SCRIBE_SESSION_SECRET`
between backends and the tokens are interchangeable, but the frontend still keeps them separate on
purpose: you almost always want a clean workspace when you switch.)

| Variable | Default | What it does |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `http://localhost:8080` | Which Scribe backend the SPA calls. |

No Meteroid credentials live here. The browser never talks to Meteroid — only to the demo backend,
which holds the API key.

### Build

```bash
npm --prefix examples/frontend run build      # tsc --noEmit && vite build  ->  dist/
npm --prefix examples/frontend run typecheck
```

## The typed client is generated from the contract

`src/api/schema.ts` is generated by [openapi-typescript](https://openapi-ts.dev) directly from
`examples/openapi.yaml` and **is committed**. Regenerate it whenever the contract changes:

```bash
npm --prefix examples/frontend run generate:api
```

Everything above it is hand-written and thin:

- `src/api/types.ts` — friendly aliases over the generated schema, plus the three narrowing helpers
  for the entitlement union. Nothing is re-typed by hand, so a contract change surfaces as a type
  error rather than a runtime surprise.
- `src/api/client.ts` — one method per operation over `fetch`, and an `ApiError` that carries the
  contract's `code`, `quota` and `upgrade_plan_code`. Twelve operations do not justify a generated
  runtime, and this way the request each screen makes is readable in one place.

Two contract details the client honours and you should not "fix":

- **Quantities are exact decimal strings** (`"3.5"`, not `3.5`). They are formatted by string
  surgery in `src/lib/format.ts` and parsed to a number only to size a meter bar. Gating is the
  backend's job, in exact decimal arithmetic.
- **Invoice money is an integer in minor units** — the one exception to the rule above, converted
  with the currency's own exponent rather than a hard-coded 100.

## What each screen demonstrates

| Screen | Meteroid surface |
| --- | --- |
| **Studio** | The metered action. Reads the `transcription_minutes` entitlement, then `POST /api/transcriptions` ingests one usage event. The 402 path is the centerpiece. |
| **Usage** | `GET /api/usage` — Meteroid's own counters for the current billing period, per metric. |
| **Plans** | `GET /api/plans` (the seeded catalog) and `POST /api/checkout` (hosted checkout redirect). |
| **Billing** | `POST /api/portal-session` (customer portal token) and `GET /api/invoices`. |
| **Workspace** | The boolean and config entitlements: `sso`, `seats`, `retention_days`, plus a raw dump of `GET /api/entitlements`. |

### Quota exhaustion is a state, not a toast

This is the part worth reading the code for. When `POST /api/transcriptions` returns
`402 QUOTA_EXHAUSTED`, the app does **not** flash a message and carry on:

- the level meter in the top rail — visible on every screen — goes red and lights its CLIP lamp;
- the composer is *replaced* by a locked panel carrying the server's own message, the live quota
  snapshot, and an upgrade button aimed at the `upgrade_plan_code` the backend resolved;
- the state stays until the entitlement actually changes.

The `402` body and `GET /api/entitlements` carry the same `QuotaSnapshot` shape, so one widget
renders both and they cannot disagree. A successful transcription returns a fresh snapshot too,
which is folded straight into local state — that is why the meter moves immediately, while
`GET /api/usage` (Meteroid's eventually-consistent counters) may lag it by a few seconds. The app
says so rather than pretending the two are transactional.

### The checkout round trip

`POST /api/checkout` returns a hosted Meteroid URL and the app redirects away from its own origin
entirely. The return URL therefore belongs to Meteroid's checkout flow, not to us, so the app does
not rely on a query parameter coming back: before redirecting it writes a `pending_checkout` marker
to `localStorage`, and on the next boot it polls `GET /api/me` (2.5s × 12) until the subscription
appears, then refreshes everything. If Meteroid has not caught up in that window the banner says so
instead of silently giving up.

### Sessions

First visit calls `POST /api/session`, which creates one Meteroid customer and returns an opaque
token; it goes to `localStorage` and every later call sends it as `Authorization: Bearer …`.
"Start a fresh workspace" on the Workspace screen drops the token and mints a new customer.

## Layout

```
src/
  api/        schema.ts (generated) · types.ts · client.ts
  state/      app.tsx — boot, actions, the quota projection · useResource.ts
  lib/        format.ts (decimals, money, timecode) · router.ts · storage.ts
  components/ Panel · LevelMeter · ErrorNotice
  screens/    Studio · Usage · Plans · Billing · Settings
  App.tsx     shell, rail, tabs, boot screen
  styles.css  the whole design system, ~200 lines of tokens and classes
```

## Design

The app is dressed as a piece of rack hardware — graphite panels, silkscreened micro-labels,
monospaced numerals — because Scribe transcribes audio and because the demo's real job is making
billing state legible. The signature element is the level meter: a metered entitlement *is* a level,
so it is drawn as one, and running out of minutes is rendered as clipping. It sits in the top rail
on every screen; entitlement state is the condition the product runs under, not a page you visit.

One accent (amber) plus three meter signal colours. Fonts are Archivo and IBM Plex Mono from Google
Fonts, with system fallbacks. Reduced motion is respected; focus is always visible.

## Known limits

- **Nothing here has run against a live Meteroid tenant.** The app is verified by typecheck, build,
  and a headless run against a mock backend that answers the contract.
- `openPortal()` opens `portal_url` with the token as a `?token=` query parameter. Meteroid's portal
  hand-off convention was not verifiable from `spec/openapi.json`; if it expects a fragment or a
  POST, that one function is where to fix it.
- Transcription history is in-memory in the backend, so it empties when the backend restarts.
- The seat and SSO controls are inert by design — they exist to show a gate, not to build a team
  feature.
